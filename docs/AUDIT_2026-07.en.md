## 1. Executive Summary

Legacy of InFest is an ambitious, unusually well-documented educational game engine: ~40,000 lines of Python across a clean-looking package layout, 68 design documents, 10 interactive teaching labs, and a 674-test suite. The breadth of intent is genuinely impressive, and the module boundaries (`engine` / `framework` / `stages`) are the right ones.

The problem is that **breadth has outrun verification**. The audit found a cluster of defects that share a single root cause: *features were written, tested in isolation, and never wired into the running game* — and nothing in the process was positioned to notice.

Three findings, taken together, mean the game as committed was not shippable:

1. **The game froze permanently the first time the player landed a hit** (AUD-001). Hit-stop set `time_scale = 0`, which drove `dt` to `0`, which meant the hit-stop countdown decremented by `0` and could never expire. Reproduced deterministically; the window stays live at 60 fps showing a frozen image.
2. **The entire damage model was unreachable** (AUD-002). The collision code read `player._current_attack_damage` — an attribute that has never existed — so `getattr`'s `1.0` fallback was used for every hit in the game. Light attacks, heavy attacks, the 3-tier combo ladder and the difficulty multiplier were all inert.
3. **Autosave destroyed campaign progress** (AUD-005). `auto_save()` rebuilt a fresh `SaveData` from six fields and overwrote the newest slot, erasing `completed_stages` — which `SceneManager._on_stage_complete` had written to that same slot microseconds earlier. Players could never bank progress.

The reason these survived is structural, and is the most important finding in this report:

> **CI had never executed a single time.** The workflow triggered on branches `main` and `develop`; the repository's branches are `prod`, `pprod` and `dev` (AUD-010). Every push and every pull request went unmatched. A failing test (`test_all_menus_return`), an unsatisfiable `requirements.lock`, and a `build-backend` that is not a real Python module all sat in the tree behind an apparently clean — because empty — CI history.

Compounding this, the test suite contained **coverage that actively concealed the bugs**. `TestCollisionSystem` asserted on a pymunk `Space` (`cs._space.bodies`, `cs.add_player(...)`) and passed — but nothing in the game ever called the methods that populate that space, so the space was empty on every real frame and the knockback the class advertised did nothing on every hit. Coverage went up; correctness went down.

**What was done.** 17 findings were fixed in place, including all five Criticals. The suite went from 644 tests with 1 failure to **674 tests, all passing**. 29 new behavioural regression tests were added, **15 of which fail against the pre-audit code** — verified by running them against a pristine checkout. A dependency-drift guard was added to CI, and CI now targets branches that exist.

**Overall maturity: 54/100 — *Pre-Alpha (Structurally Sound, Operationally Unverified)***. The architecture deserves better than its verification story. Fix the process — CI that runs, tests that assert on behaviour — and this codebase's ceiling is high.

## 2. Architecture Review — 58/100

### What is right

The three-tier split is well chosen and mostly respected:

```
src/engine/     reusable, game-agnostic: clock, event bus, scenes, input, audio, save
src/framework/  game-specific but stage-agnostic: entities, VFX, stage systems, processing
src/stages/     concrete content: stage0, boss_venado
student_templates/  the extension surface students subclass
```

`EventBus` is a clean instance-based pub/sub with a re-entrancy guard. `SaveData` uses Pydantic with genuine schema migration. The state machine in `framework/entities/states/` is a proper State pattern with one file per state. `BaseScene` gives a coherent lifecycle. These are real strengths.

### AUD-018 — Dependency inversion is violated at the layer boundary — *High*

`SceneManager` (infrastructure) imports a concrete scene at module scope:

```
src/engine/scene/scene_manager.py:16   from src.engine.scenes.title_scene import TitleScene
  -> src/engine/scenes/title_scene.py:18  from src.engine.scenes.options_scene import OptionsScene
    -> src/engine/scenes/options_scene.py:9  import pygame_gui
```

Importing the scene *manager* therefore drags in the entire scene graph plus a third-party GUI toolkit. This is not theoretical — it is exactly why `tests/test_scene_manager.py` and `tests/test_menu_navigation.py` both failed to collect with `ModuleNotFoundError: pygame_gui` on a clean install.

The class also depends on scenes in three different ways at once: a module-level import (`TitleScene`), a lazy in-function import (`EndCreditsScene`), and a `@runtime_checkable` Protocol (`_SceneWithRespawn`). Pick one — the Protocol is the right answer for all three.

> **Note on `@runtime_checkable`:** `isinstance(scene, _SceneWithRespawn)` only checks *method presence*, never signature. A scene with an incompatible `respawn(self, checkpoint)` passes the check and then raises `TypeError` at the call site. The docstring compounds this by describing the method as `_respawn` while the Protocol declares `respawn`.

**Recommended fix.** Have `SceneManager` accept a scene *factory* injected by `App`, so the manager depends on an abstraction and the composition root owns the concrete wiring:

```python
class SceneManager:
    def __init__(self, context: GameContext, *, title_factory: Callable[[], BaseScene],
                 credits_factory: Callable[[], BaseScene]) -> None:
        self._title_factory = title_factory
        self._credits_factory = credits_factory
```

### AUD-019 — Two competing routes to the event bus — *Medium*

The codebase reaches the bus two ways: dependency injection (`context.event_bus`, used by scenes) and a module-level singleton (`_get_bus()`, used by `achievements.py:12`, `checkpoint.py:17`, `base_entity.py:30`, `debug_overlay.py:14`). In production `App` calls `set_default_bus(self.event_bus)` so they coincide. **In tests they do not**, so an entity can emit into one bus while the scene under test subscribes to another — a test passes while production behaviour differs, or vice versa. This is a latent source of exactly the false confidence documented in §11.

The `event_bus` module docstring also promises module-level `subscribe()` / `unsubscribe()` / `emit()` convenience functions "for backward compatibility". **Those functions do not exist.** Only `_get_bus()` does.

### AUD-020 — `SceneManager._on_stage_complete` is a god-method — *Medium*

`src/engine/scene/scene_manager.py:105-135` does five unrelated jobs in one function: reads the player's health through a private attribute on the current scene (`current_scene._player`), computes a next-stage index, loads a save, mutates it, saves it, autosaves again, mutates `_stage_index`, and swaps the scene. It also mutates the scene stack *during* `EventBus.dispatch()`, destroying the current scene mid-dispatch.

The index arithmetic is inconsistent with itself:

```python
next_index = min(self._stage_index + 1, max(len(self._stage_queue) - 1, 0)) if self._stage_queue else 0
...
self._stage_index += 1        # unconditional, unclamped
```

The value written to the save is clamped; the in-memory value is not. At the end of the queue they diverge permanently.

### AUD-021 — Global mutable settings — *Medium*

`src/engine/core/settings.py` exposes module-level mutable state (`COLORBLIND_MODE`, `SUBTITLES_ENABLED`, `COMBO_DAMAGE_MULT: list[float]`). Any module can mutate these at runtime, they are not persisted, and they leak between tests. `COMBO_DAMAGE_MULT` being a `list` rather than a `tuple` means a stray `.append()` silently rebalances the game.

Also dead: the `REFERENCE_WIDTH/HEIGHT` branch at lines 13-16 can never be true, since `INTERNAL_WIDTH` is 800 and `REFERENCE_WIDTH` is 320.

An AST reachability scan found 81 public functions and methods defined in `src/` with no reference anywhere in the repository. Excluding framework-invoked callbacks (Pydantic validators), the pattern is not scattered dead code — it is **whole features built and never connected**:

## 3. Code Review — 49/100

### AUD-001 — Hit-stop deadlock freezes the game permanently — *CRITICAL* ✅ Fixed

**Files:** `src/framework/stage/collision_system.py`, `src/framework/scenes/stage_scene.py`, `src/engine/core/clock.py`

**Root cause.** A self-referential timer. `DeltaClock.tick()` returns `raw_dt * time_scale`. `CollisionSystem.update_hitstop(dt, clock)` decremented `_hitstop_timer` by that *scaled* `dt` and simultaneously set `clock.time_scale = 0.0`. From the next frame onward `dt` is exactly `0.0`, so `_hitstop_timer -= 0.0` leaves the timer unchanged, so `time_scale` stays `0.0`. Forever.

**Evidence — reproduced deterministically:**

```
frame  time_scale        dt   hitstop
    1      0.0000   0.01600   0.03400
    2      0.0000   0.00000   0.03400
    3      0.0000   0.00000   0.03400
   ...            (unchanged for all subsequent frames)
AssertionError: FROZEN: hitstop timer never drains -> game locked at dt=0 forever
```

**Impact.** Every `dt`-driven system stops: player, enemies, camera, animation, VFX, HUD timer, physics. Rendering is *not* `dt`-driven, so the window stays responsive at 60 fps displaying a frozen image. The pause menu still opens (input polling is frame-based), so the only escape is quitting to title. This triggers on the player's **first successful attack**.

A second, independent contributor: `_update_gameplay` captured `original_time_scale = clock.time_scale` *before* the try block, so on frame 2 it captured the already-zeroed `0.0` and "restored" that.

**Fix.** Introduced `DeltaClock.unscaled_dt` — real elapsed time, never multiplied by `time_scale` — and drove the hit-stop countdown from it. `update_hitstop` now owns `time_scale` end to end and restores `1.0` itself, removing the redundant restore path. `trigger_hitstop` uses `max()` so a second hit extends rather than truncates the freeze.

**Validation.** `tests/test_audit_regressions.py::TestHitstopDeadlock` (3 tests), including one that *asserts the deadlock still reproduces when driven with the scaled delta* — so the distinction cannot be quietly removed by a future "simplification".

**Regression risk:** Low. `unscaled_dt` is additive; `tick()`'s return value is unchanged.

### AUD-002 — The entire damage model was unreachable — *CRITICAL* ✅ Fixed

**File:** `src/framework/stage/collision_system.py:175`

```python
base = getattr(player, "_current_attack_damage", 1.0)
```

`Player` exposes `current_attack_damage` — a 15-line property folding in attack weight (0.5 light / 1.0 heavy), the `[1.0, 1.5, 2.0]` combo ladder, the difficulty multiplier and a power-up multiplier. It does **not** have `_current_attack_damage`, and never has. `getattr` silently returned `1.0` on every hit ever landed.

**Evidence:**

```
SHORT_ATTACK  designed=0.5   actually_applied=1.0   MISMATCH
LONG_ATTACK   designed=1.0   actually_applied=1.0
hasattr(player, '_current_attack_damage') = False
```

**Impact.** Light attacks dealt **2× their designed damage**; light and heavy became indistinguishable; the combo system, `COMBO_DAMAGE_MULT`, `COMBO_MAX` and the difficulty scaling were all cosmetic. The entire combat balance described in `docs/04_PLAYER_SPEC.md` never reached the game.

The property is called **only from a test** (`tests/test_combo_system.py:99`), which passed — validating dead code (see §11).

**Fix.** Read the public property. **Validation:** `TestAttackDamageModel` (3 tests). **Regression risk:** Medium — this changes real balance numbers. Short attacks now correctly deal half damage, so encounters will feel harder; the enemy HP values in `docs/05_ENEMY_SPEC.md` were tuned against the broken flat-1.0 behaviour and should be re-reviewed.

### AUD-003 — No multi-hit prevention: one swing hit up to 9 times — *CRITICAL* ✅ Fixed

**Files:** `src/framework/stage/collision_system.py`, `src/framework/entities/player.py:303`

`Player.consume_hitbox()` exists and is documented "Called by the stage collision system after an attack hitbox connects, to prevent multi-hit on the same frame." A repository-wide grep found **zero callers**. `process_attack` ran every frame the hitbox was live — ~9 frames for a 0.15 s short attack — re-applying damage each time, bounded only by the enemy's invincibility window.

**Fix.** Per-swing `_hit_this_swing` set keyed by entity identity, cleared when the hitbox retires; `consume_hitbox()` is now actually called. **Validation:** `test_a_single_swing_damages_an_enemy_only_once` drives 9 frames and asserts exactly one instance of damage.

### AUD-004 — `CollisionSystem` was a façade over an empty physics engine — *CRITICAL* ✅ Fixed

**File:** `src/framework/stage/collision_system.py`

The class docstring read: *"Physics and collision using pymunk (Chipmunk2D) rigid body simulation. Replaces the legacy SpatialGrid + manual AABB approach with a proper physics engine for knockback, hitbox detection, and spatial queries."*

Every clause was false. A grep for the methods that populate the `pymunk.Space` — `add_player`, `add_entity`, `add_static_collision`, `add_projectile`, `add_one_way_platform`, `remove_entity` — found **no production callers at all**; only tests.

**Evidence at runtime:**

```
bodies in pymunk space at runtime : 0
shapes in pymunk space at runtime : 0
_body_map size                    : 0
knockback applied? position (100.0, 72.0) -> (100.0, 72.0)   <- no movement
```

Consequences, all confirmed:

- `apply_knockback()` looked up an always-empty `_body_map` and **silently did nothing on every hit in the game**.
- `step()` integrated an empty world every frame; `update_enemies()` ran an O(n) no-op sweep every frame.
- The `_CAT_*` constants (1, 2, 4, 8, 16, 32, 64) were assigned to `shape.collision_type` — a handler-dispatch key — rather than to `shape.filter`, the actual bitmask. No handler was ever registered, so they filtered nothing. The bitmask values reveal the intent; the API used cannot express it.
- `add_one_way_platform` set `shape.sensor = True`, which generates no collision response, so it would not have worked even if called.

**Fix.** Removed the dead simulation and rewrote the module to state honestly what it does: AABB attack arbitration plus hit-stop, with locomotion explicitly delegated to the entities' own swept-AABB integrators (which were always the authoritative path). `apply_knockback` now delegates to the entity's `_knockback_velocity`, which its integrator actually reads. `draw_debug` was implemented for real.

**Regression risk:** Low-Medium. `step()`, `update_enemies()` and `remove_entity()` are retained as documented no-ops so existing stages and student templates keep working. Reinstating a genuine rigid-body pipeline is refactor item **R-03**.

### AUD-005 — Autosave destroyed campaign progress — *CRITICAL* ✅ Fixed

**Files:** `src/engine/core/save_manager.py`, `src/engine/scene/scene_manager.py`

`auto_save()` constructed a brand-new `SaveData` from its six arguments and wrote it over the newest slot. Fields the arguments did not cover — `completed_stages`, `zone_flags` — reset to defaults. And `SceneManager._on_stage_complete` does exactly this, in this order:

```python
save_data.completed_stages.append(stage_id)
sm.save(slot, save_data)          # records the completion
sm.auto_save(...)                 # immediately erases it
```

**Corroboration in the repository:** the committed `saves/slot_1.json` shows `"stage_id": "stage0"` with a real checkpoint at `(343, 471)` — a played session — and `"completed_stages": []`.

**Fix.** Read-modify-write: load the existing slot, mutate only the fields autosave owns. Also switched the timestamp to timezone-aware UTC (AUD-014) and added `fsync` before the atomic rename, so a power loss cannot atomically install a zero-length file over a good save.

**Validation:** `TestAutosavePreservesProgress` (4 tests), one of which replays the exact production sequence above.

**Remaining (not fixed):** autosave still overwrites the player's newest *manual* save rather than using a dedicated autosave slot. Tracked as **R-05**.

### AUD-006 — numba made the maths slower and broke installation — *High* ✅ Fixed

**File:** `src/engine/utils/math_utils.py`

Every easing and vector helper was a Python wrapper around an `@numba.njit` kernel. Measured, warm (JIT already compiled):

| Function | numba | pure Python | Result |
|---|---|---|---|
| `ease_in_quad` | 296.8 ns/call | 139.8 ns/call | **2.12× slower** |
| `ease_out_bounce` | 291.8 ns/call | 287.3 ns/call | 1.02× slower |

These bodies are one to five float operations; the Python↔nopython boundary crossing costs more than the arithmetic. numba also accounted for **419 ms of the module's 450 ms import time (93%)**, added ~60 MB of numba+llvmlite, and — being absent from `requirements.txt` — made the game fail to start via the documented install path.

**Fix.** Reverted to plain Python. Behaviour verified identical by 12 parametrised tests.

**Important counterpoint — where numba genuinely earns its place.** `src/framework/vfx/particle_system.py` JITs a loop over N particle arrays. Measured head-to-head against a vectorised NumPy equivalent:

| N particles | numba | NumPy | Winner |
|---|---|---|---|
| 200 | 0.0088 ms | 0.0487 ms | **numba 5.56×** |
| 1,000 | 0.0374 ms | 0.0816 ms | **numba 2.18×** |
| 5,000 | 0.1733 ms | 0.2033 ms | numba 1.17× |
| 20,000 | 0.6835 ms | 0.6800 ms | NumPy 1.01× |

So numba was kept there, but made **optional** with a NumPy fallback, and moved to a `[accel]` extra. The lesson is not "numba is bad" — it is that the same tool was applied without measurement in both places, and was right in one.

### AUD-015 — Unbounded crash loop in the main loop — *Medium* ✅ Fixed

`App.run()` caught exceptions from update and draw, called `_fallback_to_title()`, and continued. If the fallback scene itself raises, the loop spins at full speed writing a stack trace per frame indefinitely. Added a 10-consecutive-failure circuit breaker; also made a failed update skip the draw for that frame rather than drawing a half-updated scene.

### AUD-012 — Unguarded `pygame.mixer.init()` aborted startup — *High* ✅ Fixed

`app.py:47` called `pygame.mixer.init()` bare. Any machine without a working audio device — headless CI, a locked ALSA device, a VM with no sound card — crashed at launch. Now wrapped; the game continues silently.

### AUD-013 — `LOI_DISPLAY_SCALE` clipped three quarters of the screen — *High* ✅ Fixed

The display surface is created at the internal resolution with `pygame.SCALED`, but `_draw()` upscaled `internal_surface` by `settings.DISPLAY_SCALE` and blitted the result at `(0, 0)`. With `LOI_DISPLAY_SCALE=2` the game rendered a 1600×1200 image into an 800×600 window: everything outside the top-left quadrant was clipped, and two full-screen scales were paid per frame for the privilege. `SCALED` already delegates upscaling to the GPU; the blit is now 1:1.

## 4. Gameplay Review — 45/100

The design on paper is coherent: a Metroidvania with a 3-tier combo ladder, coyote time, air-dash, wall-jump, parry, hit-stop, difficulty scaling and per-attack weights. The state machine implementing it is well-factored.

**But almost none of it reached the player.** Before this audit:

- Every attack dealt a flat 1.0 damage; light/heavy weights and the combo ladder were inert (AUD-002).
- One swing hit up to nine times (AUD-003).
- Knockback did nothing (AUD-004).
- The game froze on the first hit, so none of it was observable anyway (AUD-001).

Difficulty balance therefore **cannot be meaningfully assessed from the pre-audit build** — the numbers in `docs/05_ENEMY_SPEC.md` were tuned against behaviour that no longer exists. Re-tuning after these fixes is refactor item **R-06**, and is a prerequisite to any real playtesting.

Additional gameplay findings:

- **AUD-009 — Escape in the tutorial force-started the campaign** — *High* ✅ Fixed. `TutorialScene` used one `_exit_requested` flag for both "finished the tutorial" and "pressed Escape", and both routed to `StoryScene`. A player opening the tutorial from the title menu to check the controls could not get back — Escape dropped them into a cutscene and then into gameplay. Split into an explicit `_exit_target`; CANCEL now returns to the title and is checked first so a frame carrying both CONFIRM and CANCEL cannot advance *and* exit.
- **Relics grant no bonuses.** `inventory.get_total_hp_bonus` / `_damage_bonus` / `_speed_bonus` have no callers, though the art (`assets/ui/relics/*.png`) and `docs/41_BESTIARY_CODEX.md` describe them as functional.
- **Boss Rush and Speedrun modes are non-functional** (AUD-022), both documented as delivered.
- **The HUD countdown keeps running while the game is paused** — `hud.pause_timer`/`resume_timer` exist and are never called. On a timed stage, pausing costs you the run.

## 5. UI/UX Review — 55/100

**Strengths.** Consistent scene lifecycle; a reusable `ParamPanel`; a debug overlay on F3; `keybinding_scene.py` exists for remapping; `Action`-based input indirection is the right abstraction and makes controller support tractable.

**Findings.**

- **AUD-009** (above) — the most serious UX defect: a modal screen with no way back.
- **No accessibility implementation behind the settings.** `settings.COLORBLIND_MODE` and `SUBTITLES_ENABLED` are declared and never read by any rendering or dialogue code. The options screen can toggle values that do nothing.
- **Fonts constructed per scene instance.** `TutorialScene.__init__` (and others) call `pygame.font.Font(None, N)` directly instead of the cached `AssetLoader.load_font`, rebuilding font objects on every scene construction.
- **No focus/hover state contract.** Menu scenes each re-implement selection movement (`(index ± 1) % len`) rather than sharing a widget, so keyboard/controller behaviour is per-scene and drifts.

## 6. Graphics Review — 52/100

- **AUD-013** (fixed) — the scaling path clipped the screen and cost two full-screen transforms per frame.
- **AUD-023** — 42 per-frame `Surface` allocations across 36 modules with an unused pool sitting right there.
- **Law of Demeter break in the GL path.** `App._draw` reached through `scene._lighting._surface` — two private hops from the application shell into a VFX class's internals. Replaced with an opt-in `light_surface` property plus a compatibility fallback.
- **`AssetLoader` cache is unbounded and never evicts**; keys include `scale`/`size`/`alpha`/`smooth`, so one file at several sizes multiplies entries. Combined with the global `clear_cache()` on scene exit (AUD-025), the result is thrash rather than caching.
- **`_load_sprite_sheet` returns `subsurface` views** into the cached parent. Dropping the parent from the cache does not free memory while any frame is referenced.
- **Positive:** the parallax/tint pipeline and `pyscroll` integration are conventional and sound; `get_flipped_frames` correctly caches horizontally-flipped frames instead of flipping per draw.

## 8. Performance Review — 62/100

Measured rather than assumed — and two assumptions did not survive.

**The HUD is not a hotspot.** 600 frames of `HUD.update` + `HUD.draw`: **0.048 ms/frame**, 0.3% of a 60 fps budget, 5 KiB of Python heap churn, 7 gen-0 collections. No action needed; the surface caching there is working.

**numba was a net negative in `math_utils` and a genuine win in `particle_system`** — see AUD-006 for both tables. Startup paid ~300-420 ms for the former.

**Real remaining cost centres:**

1. **42 per-frame `Surface` allocations** across 36 modules (AUD-023). This is the dominant avoidable GC pressure in the render path.
2. **`add_static_collision` created one body+shape per tile rect** with no merging — on a tile map that is thousands of static boxes. Moot now that the pymunk path is removed, but it must not return in R-03 without rect merging.
3. **`process_attack` is a linear scan over every entity, every frame**, with no broadphase. Acceptable at stage0's entity count; it will not scale, and the class previously claimed to have solved exactly this.
4. **`SaveManager.newest_slot()` fully parses all 5 save files**, and `auto_save` calls it on every checkpoint.
5. **`respawn()` re-parses the TMX and reloads assets** on every death (AUD-027).

## 17. Remediation Record — Second Pass

This section records the second pass, in which the 21 findings left open by the
first pass were closed. It also records two places where **the original audit
was wrong**, and what deeper investigation actually found.

### 17.1 Corrections to the original audit

Two findings in §12 were stated more strongly than the evidence supported. Both
are corrected here rather than quietly edited above, because a wrong diagnosis
that gets silently revised is worse than one that is openly retracted.

**Correction 1 — "Speedrun mode is non-functional" (AUD-022) was overstated.**
The `SpeedrunTimer` is in fact fully wired: `StageScene` calls `start()`,
`start_stage()`, `split()`, `stop()` and `update()`. What had no callers were
its *read* accessors — `get_formatted_time()` and `get_splits()`. So the timer
ran correctly for the whole stage and then discarded the result, because nothing
displayed it. The accurate statement is "the speedrun timer works but has no
results UI", not "the mode is non-functional". Fixed by surfacing the elapsed
time on the stage-complete banner.

**Correction 2 — the palette failures were a tooling defect, not an art defect.**
`scripts/validate_assets.py` reported eight assets with off-palette colours, and
the obvious reading was that the art needed quantising. Measuring first showed
the opposite:

```
player_idle.png     : 6 distinct colours, 0% in the declared palette
tileset_stage0.png  : 108,187 distinct colours, 1.8% in the declared palette
```

Six colours is clean, deliberate pixel art — it simply uses a *different*
palette than the table described. The art had been regenerated by
`tools/pixel_asset_generator.py` under a new colour scheme, and the table went
stale because the script its own comment told you to run —
`scripts/collect_palettes.py` — **did not exist**.

Auto-quantising, the "fix the assets" reading, would have snapped **1,029,919
tileset pixels** onto a 55-colour palette and destroyed the artwork to satisfy an
out-of-date constraint. The correct fix was to write the missing regeneration
script, refresh the tables from the current art, and replace the meaningless
palette rule for painted assets with a colour-*budget* check.

This is the clearest lesson of the whole audit: **a validator failing does not
establish which side is wrong.** Measure before you "fix".

## 19. Fourth Pass — Boss Encounter and Toolchain

### 19.1 AUD-053 — The boss declared a fight it never ran

`BossBase` knew about phases and nothing else. Everything
`docs/17_BOSS_SPEC.md` describes — telegraphing, attack variety, weak points,
summons — had no representation in code. Three concrete proofs:

**`BossPhase.attack_patterns` was a list of strings nobody consumed.**
`BossVenado` declared five patterns. `_alert_behavior` walked them in order and
fired the first one in range, so it always ran `STOMP` — first in the list and
loosest in range. The other four attacks existed in code and were never seen.

**`BossPhase.speed_multiplier` was read and thrown away**, literally:

```python
if phase.speed_multiplier != 1.0:
    pass
```

A boss that declares it speeds up in phase 2 did not speed up.

**Attacks had no wind-up.** `_do_stomp()` created the hit zone on the same
frame the attack was chosen. Without a wind-up window the player cannot read
the attack — they react from memory or not at all.

And a quieter fourth: the stomp rect was cleared by
`if self._stomp_rect.y < self.rect.bottom`, a condition that is true on the
frame it is created, because it spawns at `bottom - 8`. **The stomp was visible
and could not hit anything.**

#### What was built

`src/framework/entities/boss_kit.py` — the encounter pieces:

- **`BossAttack`** with three spans that do different jobs: `windup` (the boss
  announces), `active` (the hit), `recover` (the punish window). All three are
  explicit numbers on each attack rather than constants buried in the
  implementation, because they are design decisions and someone has to be able
  to argue with them.
- **`MIN_READABLE_WINDUP = 0.35`** — below ~0.35 s a tell is memorised, not
  read. A test fails if any attack drops under it.
- **`AttackScheduler`** actually consumes the patterns and avoids repeating the
  last attack when there is an alternative. That is not decorative variety:
  back-to-back repeats make "the boss is looping" indistinguishable from "I
  misread the tell", which breaks trust in telegraphing itself.
- **`WeakPoint`** in local coordinates, with multiplier and phase gating. It
  turns "hit the boss" into "position yourself and hit *there*".
- **`SummonTracker`** with a population cap. The cap is not an optimisation:
  without it a boss that summons every N seconds fills the screen and the fight
  stops being about the boss.

`BossVenado` now declares its encounter in one place (`_declare_encounter`):
five attacks with reasoned timings, two weak points — antlers always, flank
only in phase 2 — and one summon wave capped at four alive.

#### One design decision that cost a rewrite

The first version had the scheduler write the enemy state (`TELEGRAPHING`,
`FIRING`, `RECOVER`). It looks natural: an attack span *looks* like a state.
But `EnemyBase._run_state_machine` treats those three as states with their own
timers and **returns before running the subclass behaviour**. There would have
been two clocks governing one attack, and the boss would freeze for the whole
attack cycle — which is to say almost always, because there is almost always an
attack in flight.

The span is now read through `attack_timing`, which is pure query. The state
machine still owns the state. A test asserts exactly this and fails if anyone
returns to the intuitive version.

#### Verification

`tests/test_boss_encounter.py` — 60 tests. They do not check that the code
runs; they check design properties: that every declared attack can be read in
time, that a punish window exists, that all five attacks actually get used in
ten seconds of real combat, that weak points multiply damage *in the boss's
health* and not merely in a calculation.

They were put through **11 targeted mutations** — remove the wind-up, ignore
the summon cap, sum weak-point multipliers instead of taking the highest, drop
the speed multiplier, stop dispatching the fired attack. All 11 are now caught.
Three survived the first round and exposed tests that passed for the wrong
reason:

| Surviving mutation | Why the test missed it |
|---|---|
| Weak points: take the last instead of the highest | The test declared points in one order only, and the highest happened to be last |
| Aggro gate: attacking without having seen the player | The test never set `_player_ref`, so it exited on an earlier check |
| Not executing the dispatched attack | The test measured that the hook was called, not that anything happened in the world |

All three were fixed and now fail against their mutation.

### 19.2 AUD-054 — Four editor errors on correct code

The editor reported, on `src/engine/core/save_data.py`:

```
E0401  Unable to import 'orjson'                (Pylint)
       Import "pydantic" could not be resolved  (Pylance)
C0114  Missing module docstring    (in a file that opens with a docstring)
C0116  Missing function docstring  (on methods that have one)
```

**None of the four pointed at a defect in the code.** orjson 3.11.9 and
pydantic 2.13.4 are installed in `.venv/Lib/site-packages`, which is why the
game starts. What was missing is that the project had **no
`.vscode/settings.json`**, so Pylance and Pylint analysed with the global
Python (`C:\Python314\python.exe`) instead of the project environment. The last
two came from an unconfigured Pylint, whose defaults demand a docstring on
every public method — something ruff, the linter that actually runs in CI, does
not require — and they pointed at line numbers that no longer exist in the
file: stale diagnostics.

Worth stating outright, because the natural reaction was to edit
`save_data.py` — that is, to change correct code to quiet a mis-aimed tool.

#### What was fixed

1. **`.vscode/settings.json`** pins the interpreter to `.venv`, enables ruff,
   disables Pylint in the editor, and forces `files.eol: "\n"` — the last one so
   a save from Windows cannot convert the tree back to CRLF, which is what
   produced a 334-file diff with no real change in it.
2. **`[tool.pylint]` in `pyproject.toml`** aligns Pylint with ruff: 120 columns,
   no docstring demands, and `extension-pkg-allow-list` for orjson, pygame,
   pydantic_core, numpy and cv2 — without it Pylint cannot inspect compiled
   extensions and states falsehoods at error severity (`E1101: Module 'orjson'
   has no 'dumps' member`). With the config, `save_data.py` scores **10.00/10**.
3. **`.flake8`** was a third linter with its own rules that nothing ran, and
   `CONTRIBUTING.md` told contributors to use it. It now mirrors the ruff values
   exactly and says in its header that it is not the source of truth;
   CONTRIBUTING points at ruff in both languages.
4. **Preflight in `main.py`**: checks the six dependencies that gate startup and,
   if any is missing, says which one, **which interpreter is running**, and how
   to activate `.venv`. Previously, launching with the wrong Python produced a
   `ModuleNotFoundError` mid import-chain with no hint that the interpreter was
   the problem.
5. **`--stage`/`--boss` diagnosis**: `except ModuleNotFoundError` reported "stage
   not found" both when the stage did not exist and when it existed but one of
   its imports failed. The message sent you looking in the wrong place; it now
   distinguishes the two via `exc.name`.

#### Pylint as a second pair of eyes

With the config aligned, Pylint was run in `--errors-only` mode over all of
`src/`, `main.py`, `scripts/` and `tools/`. Eight findings: seven false
positives with understood causes, and **one real**:

`src/engine/ui/minimap.py` created `_bg_surf` inside `draw()` behind a
`hasattr(self, '_bg_surf')`. Between constructing a `Minimap` and drawing it,
the object had a different attribute set — any code that inspected it (a test, a
debug panel, a serialiser) saw one shape or the other depending on timing. It is
now declared as `None` in `__init__` and created lazily. An attribute that is
sometimes `None` is easier to reason about than one that sometimes does not
exist.

The seven false positives were silenced **locally and with justification**, not
globally: `Player`'s `__getattr__`/`__setattr__` proxy (which Pylint cannot
follow), the `hasattr` guard in `_resting_state`, and `__dataclass_fields__` in
`UserSettings`. Disabling `no-member` or `access-member-before-definition`
project-wide would have thrown away real signal along with the noise.

**Result: 0 Pylint errors across the project, 0 ruff findings.**

`tests/test_toolchain_consistency.py` — 9 tests that stop the tools from
